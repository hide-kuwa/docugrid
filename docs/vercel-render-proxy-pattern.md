# Vercel + Render 中継パターン

最終更新: 2026-07-15

このメモは、**Vercel をブラウザ側の入口にして、Render 上の FastAPI を裏側に置く** 構成を採るときの運用ルールです。

想定する流れ:

```text
Browser -> Vercel (Next.js / Route Handlers) -> Render (FastAPI) -> storage
```

## ねらい

1. ブラウザから Render を直接触らせず、API の入口を Vercel に寄せる
2. 秘密情報や署名付き処理を Vercel のサーバー側に閉じる
3. 読み取り系 API だけ Vercel でキャッシュして、Render の負荷を落とす
4. 本番サービスと外部公開導線を分けて、障害伝播を小さくする

## 1. Vercel を中継にする

ブラウザから Render の API を直接呼ばず、Vercel の Route Handlers / API Routes を経由させます。

この構成にすると:

- API キーや署名用の秘密をブラウザに置かずに済む
- CORS の設定を単純化できる
- 認証ヘッダや Cookie の取り扱いを Vercel 側で集約できる

この repo では現状、フロントが `NEXT_PUBLIC_API_BASE` を使って直接 API を呼ぶ実装になっています。  
全面的に中継化する場合は、`frontend/src/lib/api-auth.ts` と `frontend/src/config/api.ts` の前提を見直して、Vercel 側の BFF に寄せる必要があります。

## 2. キャッシュは読み取り専用だけに限定する

Vercel のキャッシュは、**GET の公開データ** かつ **ユーザー個別性のないレスポンス** に限定します。

安全な対象:

- プレスリリース一覧
- 固定ページ
- 公開カタログ
- 変更頻度の低い参照データ

避ける対象:

- 認証必須の個人データ
- firm / client ごとに変わるレスポンス
- POST / PUT / DELETE
- CSRF が絡む操作

キャッシュ期間は短めから始め、変更頻度と障害影響を見ながら延ばします。  
大量アクセスを吸収したいなら、まず Vercel 側で静的化できるところを増やし、Render へ流すリクエスト数を減らします。

## 3. リージョンは近いものを選ぶ

Vercel の実行リージョンと Render の配置リージョンは、可能な範囲で近づけます。

ルールは単純です。

- 日本向けなら、日本に近い利用可能リージョンを優先する
- 取れない場合は、Render と Vercel の両方で最も近い選択肢を合わせる
- 重要なのは「片方だけ遠い」状態を避けること

レイテンシはユーザー体験だけでなく、API 連携やタイムアウト再試行にも効きます。

## 4. 本番サービスと広告・公開導線を分離する

同じ API や DB を共有するなら、Vercel 側で入口制御を入れます。

推奨事項:

- 入口用の API キーを別発行する
- 公開導線ごとに権限を絞る
- レート制限を Vercel 側でも掛ける
- 重要な更新系 API は直通させず、追加の検証を入れる

狙いは、公開導線のスパイクや不正アクセスが本番サービスへ波及するのを防ぐことです。

## この repo での実務上の注意

- `backend/storage/` は永続ディスク前提です
- Render 側は FastAPI + 永続ボリュームを持つ前提にします
- Vercel はフロントと中継層を担当し、永続状態は持たせません
- 既存のブラウザ直叩き API を残すなら、プロキシ化は段階導入にします

## 使い分け

この構成が向くケース:

- 公開サイトや広告サイトの裏で、少数の API を安全に見せたい
- 読み取り系トラフィックが多く、API 負荷を Vercel で吸収したい
- 秘密情報をブラウザへ一切出したくない

この構成が重いケース:

- 画面が API だらけで、全面 BFF 化が必要
- 認証・Cookie・CSRF の整合を一気に作り直す必要がある
- すぐに管理画面を本番化したい

その場合は、まず `frontend -> Render` の直通で本番化し、必要な箇所だけ Vercel 中継へ寄せる方が早いです。
