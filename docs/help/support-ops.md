# サポート運用（CS・電話ポリシー）

要約: CS は **メールが基本**。電話は例外。アプリのチケット（`/api/support/tickets`）と指標（`/api/support/metrics`）で品質を見ます。一般ユーザー向け窓口説明は [support.md](./support.md)。

対象: CS・所長・運用担当

---

## 原則

1. **メール優先** — 経緯が残る・共有できる・コストが低い  
2. **電話は最終手段** — 業務停止級、またはメール往復でも再現・権限確認が進まないとき  
3. **アプリに電話番号を常時出さない** — 必要なとき CS がメールで案内する  

---

## チケットの扱い

| 状態 | 意味 |
|------|------|
| `open` | 受付・調査中 |
| `resolved` | メール等で解決（クローズ前） |
| `closed` | 完了 |
| `phone_requested` | 電話対応が必要と判断（CS 側メモ） |

ユーザーはサポートパネルからチケット作成。firm 横断は不可（サーバで `firm_id` を強制）。

状態更新 API は **firm-wide ロール**（admin / firm_admin / approver 等）のみ。

---

## 電話に上げてよい条件（チェック）

次の **いずれか** を満たし、かつ **メールチケットが既にある** こと:

- [ ] 事務所全体でログイン不能・保存全滅など業務停止級  
- [ ] メール 2 往復以上でも再現手順や権限が確定しない  
- [ ] ユーザーが電話を希望し、CS も口頭の方が早いと判断  

満たさない場合はメール継続。番号は折り返しメール本文で案内。

---

## 見る指標（`GET /api/support/metrics`）

事務所単位:

- 総チケット数 / open / resolved_or_closed  
- **resolution_rate** … 解決寄り件数 ÷ 総数  
- **phone_rate** … 電話関連 ÷ 総数（低いほどメール優先が効いている）  
- kind / status / email_status の内訳  

週次で phone_rate が急増したら、ヘルプ記事不足や再現テンプレ不足を疑う。

---

## ヘルプ品質との関係

ボット／検索の当たりは `docs/help` の厚さに依存します。  
チケットで同じ質問が繰り返されたら、対応するヘルプを `draft`→厚くする（coverage 更新）。

---

## 環境（メール送信）

- `DOCUGRID_SUPPORT_INBOX_EMAIL`  
- `DOCUGRID_SUPPORT_SMTP_*`  

未設定でもチケットは SQLite に残ります。本番 CS 運用開始前に inbox + SMTP を必須にする。
