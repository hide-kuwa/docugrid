# サポート AI チャットボット構想

最終更新: 2026-08-08

**ゴール:** ユーザーが「わからない・動かない」ときに、まずアプリ内チャットで解決し、必要なら CS へスムーズにつなぐ。

本ドキュメントは実装前の正本。ヘルプ Markdown（`docs/help/*.md`）はボットの知識源として育てる。

---

## 1. 体験の流れ（必須）

```
ユーザー
  │
  ├─① チュートリアル（スポットライト） … 初回の「押し所」
  │
  ├─② ヘルプ記事（docs/help → 将来 /help） … 自分で読む
  │
  └─③ AI チャット（本構想）
        │
        ├─ 使い方・チュートリアル案内（ヘルプ / ツアー起動）
        ├─ 不具合報告（再現手順・画面・firm メタをチケット化）
        ├─ AI で解決できそう → 手順・リンク・ツアー再開
        └─ AI で解決不能と判断
              │
              └─④ CS エスカレーション
                    │
                    ├─ 基本: メール（スレッド継続・履歴残す）
                    └─ メールで足りないときのみ: 電話
```

電話を最初の窓口にしない。コストと記録性のため **メール優先**。

---

## 2. ボットの役割（やる / やらない）

| やる | やらない |
|------|----------|
| `docs/help` に基づく使い方案内 | 税務判断・法令の最終回答（「税理士に確認」へ） |
| 該当ツアー（`FeatureTour`）の起動提案 | 他社・他 firm のデータ参照 |
| 画面ラベルと手順の言い換え | パスワードや秘密鍵の受け取り |
| 不具合のヒアリング → 構造化レポート下書き | 本番データの無断変更 |
| 「CS にメールする」導線（下書き生成） | いきなり電話番号を出す（条件付きまで） |

---

## 3. エスカレーション判定（AI → CS）

ボットが次を満たしたら **メール CS** を提案（ユーザー同意後に送信 or mailto / フォーム）:

- 同じ質問を繰り返しても解決しない（例: 2 ターン以上「まだダメ」）
- ユーザーが明示的に「人に聞いて」「不具合報告」
- エラーコード・権限・課金・データ消失など高リスク
- ヘルプ coverage が `stub` / 欠落で根拠記事がない
- 自信スコアが低い（実装時の閾値は別途）

**電話**は次のときだけ案内（CS 側がメールで判断してもよい）:

- 業務停止級（ログイン不能が事務所全体、保存全滅など）
- メール往復でも再現・権限確認が終わらず、口頭の方が早いと CS が判断
- ユーザーが電話を希望し、かつメールチケットが既にオープン

電話番号はヘルプに常時大きく出さず、「CS がメールで折り返し時に案内」を基本にする。

---

## 4. チャネル設計

| 段階 | チャネル | 実装イメージ |
|------|----------|----------------|
| L0 | アプリ内チャット UI | `support.assistant` feature surface |
| L1 | 知識 | `docs/help/*.md` + coverage（RAG 可。既存 `rag` と分離 or 専用 collection） |
| L2 | 不具合チケット | `POST /api/support/tickets`（firm_id・user・画面・本文・severity） |
| L3 | メール CS | チケット → サポート inbox（SendGrid 等）。返信はメール |
| L4 | 電話 | CS 運用。アプリは「電話対応が必要な場合はメールでご案内」とだけ書く |

開発中は L2 をログ／SQLite でも可。本番はメール到達を必須にする。

---

## 5. データ・認可

- `firm_id` / ログインユーザーは JWT から。ボットが別 firm を装わない
- チャット履歴は firm スコープで保存（保持期間はポリシーで）
- 不具合報告に含めてよい: 画面名、period、エラーメッセージ、時刻、（任意）doc id
- 含めてはいけない: 生パスワード、フル PDF 本文の無制限添付（必要なら版 ID のみ）

既存 tenancy ルールに従う。フロントだけの「サポート」は不可。

---

## 6. UI 配置（案）

- 左レール **ヘルプ** ホバー → ヘルプセンター / ガイド / **サポートチャット**
- 初回はツアー優先、必要ならチャットで記事・ツアーを提案
- `/help` 各記事の末尾に「チャットで聞く」→ 記事 ID をコンテキストに渡す（後回し可）

## 8. ヘルプ執筆との関係（重要）

ボットの品質 ≒ **coverage が draft/ok の記事の質**。

- 機能 PR で `docs/help` を更新する現行ルールは、そのまま **ボット KB 更新**でもある
- 記事には「チャットに聞かれたとき用」の短い **要約段落**を冒頭に置くとよい（今後の執筆ルール）
- `n/a` の機能はボットも「対応外」と答える
